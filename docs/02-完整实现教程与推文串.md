# 教程二：从一道菜到40秒广告，Omni Food Ad Studio是怎样实现的？

更新日期：2026-09-07。第一部分是可用于长文的完整流程讲解；第二部分是可拆分发布的推文串。这里描述的是现有Skill及脚本的真实分工，不宣传无人值守或无条件商用。

## 一、完整实现教程

### 1. 先把“一键”拆成可检查的工作流

这个Skill不是视频生成模型，也不是一个包办全程的服务器。它让Codex读取规则、理解素材，调用研究渠道、浏览器和本地脚本，串起以下顺序：

菜名／自有素材 → 研究与选片确认 → 40秒语义参考 → 四段视频＋20张图 → 四组提示词 → 逐段Flow生成与人工确认 → 口播稿确认 → 连续TTS → 合成验收 → 封面确认 → 带封面MP4。

其中，“生成什么、该在哪里暂停”由Codex按Skill决定；“裁多少秒、音频有多长、视频能否完整解码”交给确定性的本地工具计算。

### 2. Skill目录就是工作流说明书

`SKILL.md`定义默认参数、执行顺序和人工关口；`references`分别说明来源、提示词、Flow操作、混音及验收；`scripts/pipeline.py`负责本地媒体阶段；`scripts/doubao.mjs`负责连续旁白；`tests`验证部分错误输入能被拒绝。

人工审批目前由代理核对并写入项目记录，不是命令行脚本自带的审批引擎。这意味着不能看到几条命令就整串运行，也不能把脚本成功当用户确认。

### 3. 建一个独立菜品项目

`pipeline.py init`创建素材、参考、提示词、生成视频、输出、证据目录，以及项目参数和待填写清单。已有项目不会被当作新项目直接覆盖。

研究记录写入 `research.md`；工序剪辑写入 `edl.json`；模型及资产来源写入 `generation.json`；权利证据写入 `rights.json`。`approval.json`由代理维护，用于记录用户确认的具体版本。

### 4. 先研究做法，再让人选素材

Agent Reach先doctor检查渠道，再通过当前可用渠道研究菜谱和视频。不同地区做法可能不同，不能把冲突配方拼成所谓“标准答案”。明确克数才计算重量比，“适量”仍保留适量。

Codex列出视频候选的标题、作者、链接、时长、工序完整度与许可状态。用户选择并确认使用范围后，才下载和处理。公开可看、下载成功、上传成功是三种技术事实，都不自动等于许可。

自有实拍素材可以跳过选片下载，但本地处理与上传外部AI仍需明确范围。换源后重新记录，不混用旧片的授权证据。

### 5. 把长教程变成40秒“制作逻辑”

核心不是平均切成四份，而是先理解动作：原料处理、关键火候、焖煮或合炒、出锅成品。不同菜品应调整段落，不把炖鹅套进快炒模板。

EDL记录每个源时间范围、输出时长、语义标签。脚本据此剪切与变速，并检查范围越界、倒序、重复、每段10秒以及关键图时间点。普通长教程中的重复铺垫被删，必要过程保留。

当前prepare脚本输出的参考规格为720×1280/24fps，横屏源保留内容并留边，避免裁掉手和锅；最终广告才统一为1080×1920。用户提供已剪好的40秒竖片并要求四等分时，可按用户明确切点做专项处理，不能把这个个例当默认算法。

### 6. 每段五图：选“状态”，不是随机截图

每段选择五个看得清的动作或状态，例如入锅、翻转、变色、挂汁、装盘。20张图共同约束食物形态、工具和熟度；10秒参考视频则提供动作先后与节奏。

图像要避开模糊和严重遮挡，不能只抓首帧，也不应自动擦除水印来解决版权问题。文件哈希帮助追踪后续是否换过素材，但不能证明拥有版权。

### 7. 写四个能独立成立的提示词

每个场景都单独写清菜品形态、锅盘材质、台面、光向、熟度起点和终点。不能只写“和上一段一样”，因为不同生成请求未必共享完整上下文。

提示词明确：一段参考视频负责工序节奏，五张图分别负责哪些视觉事实；再按0–3秒、3–7秒、7–10秒描述有限动作和运镜。限制字幕、无关品牌、额外食材、反常手部和不合理的生熟跳变。

高级感主要靠可读的动作、真实食物色泽、克制景深与光线，不靠堆满“电影感”形容词。实际图片和视频必须支持提示词说的内容。

### 8. Flow上真正附加“一段视频＋五张图”

Codex通过已授权浏览器进入Flow，核对实际模型标签、10秒、9:16、单个输出、额度和分辨率。逐个确认六项附件已进入当前提示词，而不是仅存在于素材库。

附带本地脚本并不负责这一步网页生成。已知仅图片参考的CLI不能冒充联合视频参考；当前账户不支持时，暂停而非偷偷降级。

每段只提交一次，记录任务ID。任务完成但下载失败，先恢复下载、检查文件，不急着再次扣费。最高可用下载质量以页面为准，720p转1080p明确标注升采样。

### 9. 逐段人工确认，避免错误扩散

第1段下载后先技术检查和抽帧，再给用户看完整片段。用户明确确认后才生成第2段；第2→3、第3→4一样执行。第4段也必须确认。

允许提前准备提示词，不允许提前排队生成。用户不满意时只处理当前段；新版本重新确认。技术通过只说明文件能用，不代表镜头符合用户意图。

### 10. 按真实画面写稿，先确认再配音

四段全部确认后，才根据画面写完整口播。约140–175汉字只是初稿起点，最终以实际语音时长为准，不为了字数牺牲表达。

用户修改的稿件先保存；仅“修改如下”不等于定稿。用户明确说“确认无误，开始”后，记录文本哈希并按原文制作。后续因时长要改词，重新请用户确认。

### 11. 一次连续豆包TTS，避免四段拼音色

`doubao.mjs`读取确认稿和私密配置，只发起一条连续请求。脚本接收完整音频数据，再转换成WAV；输出已存在时拒绝直接再次调用，减少误重复计费。

它只处理起始静音，不硬裁结尾。原音频保留，后续测量真实时长再做轻微语速调整。服务密钥只在本机配置中使用，不进入公开项目。

### 12. 给40秒留出真正的尾音空间

默认使用39秒的人声窗口，开头延迟约0.2秒，结尾至少0.8秒保护。语速系数按“原旁白时长÷39”计算，允许范围0.88–1.18。

超出范围就返回改稿并重新确认，不把末句硬切掉。调整后再次测量实际音频，不能只信公式。人声不做尾部淡出，保留最后一个字。

### 13. 四段合成，前景人声与背景环境声分工

`pipeline.py finish`按顺序拼接四段10秒视频，统一1080×1920、24fps，编码H.264与AAC。旁白响度目标约-16 LUFS，环境声低音量混入。

原声如果含未知音乐、对白或没有完成必要检查，明确记录后静音，不为了氛围把参考片的版权音轨带进广告。最终40秒不靠补静帧或反复循环来凑时长。

### 14. 验收分三层，不用一个“通过”包办

技术层：时长、分辨率、960帧、编码、完整解码、黑场、人声尾部、响度和峰值。关键帧覆盖普通镜头、转场两侧和末秒。

创意层：手和食物是否变形、工序是否合理、成品是否诱人、配音是否读对且完整。音量检测不能替代听音。

权利层：素材、外部上传、商业改编、模型用途、音色、人像商标与音乐来源。技术和创意通过不自动等于商业许可齐全。

报告分别给出 `technical_pass`、`creative_pass`、`commercial_ready`。用户替换生成片段时，没有新的模型证据就如实保留缺口，不能继承旧任务ID来伪装。

### 15. 封面先让人看，再嵌入视频

从最后成品镜头导出封面并展示，用户确认可用后，直接嵌入MP4作为附加封面图，另存带封面版本。

这里不是把图片塞进视频开头：40秒内容和配音不变。新旧主视频和音频流分别比较哈希，检查封面标记 `attached_pic=1`，另存封面验收记录。原MP4和独立图片都保留。

平台可能忽略内嵌图片，所以还要提供封面JPG。封面好看或用户确认封面，不等于商用权利已经完成审核。

### 16. 这次迭代真正固化了什么

我们把客家碌鹅制作中的要求变成可复用规则：素材先选、视频逐段确认、口播先定稿、封面先确认，确认记录跟随文件版本。

现有客家碌鹅项目完成过四段Flow镜头、连续TTS、本地40秒合成、用户指定第四段替换和MP4封面嵌入。新的逐段确认规则是在迭代后固化的，不能倒过来宣称早期每段都经过同样的人审流程。

旧目录里的多个菜品与验收文件属于经验来源，不等于已经验证12次“从菜名到联合参考生成”的全链路。对外展示应只说真实做过并能提供证据的事。

## 二、可直接拆分发布的中文推文串

以下是逐条发布稿；可按平台字数限制进一步拆分。只介绍工作流，不包含私人路径、真实密钥、第三方视频素材或未经核实的商业承诺。

### 01｜开篇

我把“从一道菜到一支40秒竖屏广告”的流程整理成了 Codex Skill：omni-food-ad-studio。

它串起资料研究、参考剪辑、Flow镜头生成、豆包旁白和带封面MP4。输入可以只有菜名，但关键环节必须人来确认，不是无人值守的黑盒。

### 02｜先研究，不急着生成

第一步先让Agent Reach检查渠道，再整理菜谱、配比、工序与视频来源。

同一道菜可能有不同地方做法，要选一个一致版本。不是把搜索结果里所有配料拼到一起，更不是只凭菜名凭空写制作过程。

### 03｜参考视频由我选

Codex先列候选：作者、链接、时长、工序完整度和授权状态。

我选定并确认使用范围后才下载。自有实拍可直接提供，但“本地剪辑”和“上传外部AI”仍分别明确。公开视频不等于能随意商用。

### 04｜40秒不是平均分割

长教程先按真实动作压缩：备料、关键火候、焖煮或收汁、成品。

必要过程合理加速，重复内容删掉，再组织成四段各10秒。目的是保住制作逻辑，不是只把原视频快放完。

### 05｜一段视频＋五张图

每个10秒片段选出五个清晰状态，共20张参考图。

视频约束动作先后，图片约束食材形态、熟度和器皿。取图看语义，不是每隔两秒随手截一张。

### 06｜提示词必须独立成立

四组提示词都写清厨具、光线、食物状态、分秒动作和结尾衔接。

不能只说“与上一段一样”。模型不一定记得上一段，稳定的视觉事实要在每次请求里明确写出来。

### 07｜附件真的加进去了吗？

Flow素材库里有文件，不代表这次生成已经引用它。

每次都核对一段视频和五张图已附加，再检查模型、10秒、9:16、输出数量和费用。能力不支持就暂停，不悄悄丢掉参考。

### 08｜一段确认后才做下一段

这是这次最重要的规则之一：第1段先让我看片，确认无误后才生成第2段；一直到第4段都如此。

不提前排队、不把自动检查当我的确认。某段有问题，只处理当前段，避免错误一路传下去。

### 09｜下载失败不等于生成失败

平台已生成但下载卡住，先找回同一任务的结果，不马上重新计费。

分辨率也如实记录：720p升到1080p只是交付尺寸变化，不能宣传为原生1080p。

### 10｜先定稿，再开口

口播稿根据最终镜头写。必须我确认原文无误后，才开始配音和合成。

我发修改稿不等于自动同意开工；定稿后也不能为了时长偷偷改词。需要改，就再确认一次。

### 11｜旁白一次生成

豆包TTS读整份稿件，一次生成连续旁白，不拆成四条再拼。

生成后测实际时长，再轻微调语速。40秒里留出起始与末尾保护，不硬切最后一个字，也不淡出人声尾句。

### 12｜机器验什么，人验什么

机器查时长、帧数、解码、黑场、响度和峰值。

人看食物、手部、工序和成品，听读音与末句。技术检查通过不代表创意通过，更不代表版权和商用授权都已解决。

### 13｜封面不是片头

从成品镜头导出封面，先给我确认。确认后直接嵌入MP4，另存带封面版。

不加一秒静帧，不改变40秒画面和配音。独立封面图也保留，因为有些发布平台不会读取MP4内嵌封面。

### 14｜真正可复用的是边界

这个Skill的价值不只是几组提示词，而是：知道何时调用工具、何时暂停、如何记录来源、如何续跑，以及如何承认没验证的部分。

菜名让流程开始，人工确认把关质量。最终交付视频，也交付可以复查的过程。
